## Superfície de ataque

- **Ativos**: chave da API da Anthropic (dinheiro); `GITHUB_TOKEN` com escrita no repositório público (reputação, código); token do agendador externo (só *Actions*); conteúdo publicado (confiança dos leitores). O app guarda só dados locais não sensíveis: preferências, progresso, salvos e lembrete.
- **Pontos de entrada**: 23 feeds/APIs externos (RSS, arXiv, bioRxiv, HF), cujo conteúdo é não confiável e vai para o LLM; o JSON publicado no GitHub Pages, consumido pelo app; os links abertos pelo app; as dependências instaladas a cada execução.
- **Fronteiras de confiança**: feeds → runner do GitHub Actions (com segredos) → LLM → JSON público → celular. O app não tem segredo nenhum e só lê conteúdo público.

## Achados

### SEC-001 · [Médio] Dependências do pipeline sem versão fixa num job com segredos
- **Local**: `pipeline/pyproject.toml:6-15`, `.github/workflows/daily-content.yml:46-47`
- **Categoria**: OWASP A06/A08 (componentes vulneráveis, integridade de software), CICD-SEC-3
- **Descrição**: o workflow diário roda `pip install -e pipeline` com faixas `>=`, então cada execução instala a versão mais nova de cada pacote e das dependências transitivas. Esse código roda no mesmo job que recebe `ANTHROPIC_API_KEY` e um `GITHUB_TOKEN` com `contents: write`.
- **Cenário de exploração**: um atacante publica uma versão maliciosa de uma dependência transitiva (sequestro de conta do mantenedor, já visto no PyPI). Às 05:00 o job instala essa versão; o código lê a variável de ambiente com a chave, ou o token salvo pelo `actions/checkout`, e envia para fora.
- **Impacto**: gasto na conta da Anthropic e push de código no `main` de um repositório público.
- **Correção recomendada**: arquivo de lock com hashes (`pip-compile --generate-hashes`) instalado com `--require-hashes`, no workflow diário e no CI. Atualizações passam a ser explícitas, num commit revisável.
- **Teste sugerido**: o CI instala pelo lock com `--require-hashes`; um teste confere que toda dependência do `pyproject.toml` está no lock.
- **Status**: Corrigido
- **Correção**: `pipeline/requirements.lock` (pip-compile, 30 pacotes com hashes); o workflow diário instala com `--require-hashes` e roda o código pelo `PYTHONPATH`, sem build do pacote. O CI valida o lock no Linux · testes: `tests/unit/test_workflows.py::test_daily_run_installs_locked_dependencies_with_hashes`, `::test_lock_covers_every_runtime_dependency`

### SEC-002 · [Baixo] Etapa que processa conteúdo externo tem permissão de escrita no repositório
- **Local**: `.github/workflows/daily-content.yml:23-24,38`
- **Categoria**: CICD-SEC-5 (permissões excessivas)
- **Descrição**: `contents: write` vale para o job inteiro, e o `actions/checkout` guarda o token no `.git/config`. A etapa que roda o pipeline (parsers de feeds e SDKs) tem acesso a ele, embora só a etapa de publicação precise.
- **Cenário de exploração**: uma falha num parser (ou o SEC-001) dá execução de código durante a coleta; o atacante usa o token já presente para fazer push no `main`.
- **Impacto**: alteração do código ou do conteúdo publicado.
- **Correção recomendada**: dividir em dois jobs: `generate` (`contents: read`, sem token persistido) gera o site como artefato, e `publish` (`contents: write`) só faz o push no `gh-pages`, sem rodar código de terceiros.
- **Teste sugerido**: teste do workflow que confere que o job que recebe `ANTHROPIC_API_KEY` tem `contents: read` e `persist-credentials: false`.
- **Status**: Corrigido
- **Correção**: job `generate` (`contents: read`, checkout sem credencial, gera o site como artefato) e job `publish` (`contents: write`, só `rsync` + `git push`); `permissions: {}` no topo · testes: `test_workflows.py::test_job_with_api_key_cannot_write_to_the_repository`, `::test_job_with_write_access_runs_no_project_code`

### SEC-003 · [Baixo] Actions referenciadas por tag, não por commit
- **Local**: `.github/workflows/ci.yml`, `.github/workflows/daily-content.yml` (`actions/checkout@v5`, `actions/setup-python@v6`, `actions/setup-node@v5`)
- **Categoria**: CICD-SEC-8 (integridade de terceiros)
- **Descrição**: tags podem ser movidas. As actions são oficiais da organização `actions`, o que reduz bem o risco.
- **Correção recomendada**: fixar pelo SHA completo, com a tag em comentário.
- **Teste sugerido**: teste que confere que todo `uses:` tem um SHA de 40 caracteres.
- **Status**: Corrigido
- **Correção**: todas as actions fixadas por SHA, com a tag em comentário · teste: `test_workflows.py::test_actions_are_pinned_by_commit_sha`

### SEC-004 · [Baixo] Redirecionamentos de feeds podem cair para http
- **Local**: `pipeline/src/one_percent/sources/__init__.py:40-47`
- **Categoria**: OWASP A02 (falha criptográfica em trânsito)
- **Descrição**: `follow_redirects=True` aceita um redirecionamento de `https` para `http`, e o feed passa a ser lido sem TLS.
- **Cenário de exploração**: alguém na rota entre o runner e a fonte injeta um feed falso. O texto vira resumo e é publicado, e o link do item é publicado como `https` para um domínio escolhido pelo atacante.
- **Impacto**: conteúdo falso ou link malicioso num card do dia.
- **Correção recomendada**: rejeitar a resposta se `response.url.scheme != "https"`.
- **Teste sugerido**: `test_rejects_redirect_to_plain_http` com `MockTransport` respondendo 301 → `http://`.
- **Status**: Corrigido
- **Correção**: `fetch_bytes` rejeita resposta final fora de https; as 23 fontes reais continuam funcionando (coleta de 16/11: 1047 itens, nenhuma falha) · teste: `tests/integration/test_rss_source.py::test_rejects_redirect_to_plain_http`

### SEC-005 · [Info] Prompt injection pelos feeds (LLM01/LLM02): risco residual baixo
- **Local**: `pipeline/src/one_percent/summarizer/anthropic.py`, `publishing/cards.py`
- O conteúdo vai entre delimitadores com HTML escapado, o prompt manda tratar `<item>` como dado e a saída é JSON com schema. O modelo não tem ferramentas. URL, autores e datas vêm sempre da fonte, e o app mostra os textos como texto puro e só abre `https`. No pior caso, um item malicioso muda o texto do próprio card. Nada a corrigir.

### SEC-006 · [Info] `npm audit` moderado só em ferramentas de build/teste
- `glob`/`minimatch` (ReDoS, cancelamento de timeout) chegam via Jest e `@expo/fingerprint`, que rodam na máquina de desenvolvimento e no CI com padrões definidos pelo projeto. Nada disso vai para o APK. As "correções" sugeridas pelo npm são downgrades para versões antigas do SDK. Acompanhar as próximas versões do Expo.

### SEC-007 · [Info] Armazenamento local e permissões do app
- O AsyncStorage não é criptografado, mas só guarda dados não sensíveis. O app não tem login, chave nem dado pessoal. Permissões Android: `POST_NOTIFICATIONS` e `RECEIVE_BOOT_COMPLETED` (do lembrete), nada além.
